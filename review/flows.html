Data Flows — Truy vết luồng dữ liệu

Tab "Flows" liệt kê các luồng truy vết từ endpoint HTTP → controller → service → repository → DBModel. Toàn bộ là thuật toán BFS thuần client-side (lib/dataFlow.ts), không gọi API — chỉ dùng quan hệ có sẵn trong graph đã tải.

Bước 1 — Tìm endpoint có thể trace (listTraceableEndpoints)

  • Duyệt cạnh HANDLES_ROUTE: đầu là Method/Constructor = handler, đầu kia = endpoint. Bỏ nếu không có đầu nào là Method/Constructor.
  • method = prop httpMethod của handler, else parse từ tên endpoint dạng "GET /api/x"; path = prop routePath, else phần sau verb.
  • Fallback khi không có HANDLES_ROUTE: quét mọi node Method có prop httpMethod trực tiếp.
  • Sắp xếp theo path rồi method (deterministic).

Bước 2 — BFS trace tới database (traceFromIndex)

Dựng adjacency outByNode gộp 3 nhóm cạnh, đi bình đẳng (không ưu tiên loại):

Nhóm cạnhLoạiVai trò
CALL_EDGESCALLSLời gọi phương thức.
RESOLVE_EDGESIMPLEMENTS, OVERRIDESBắc cầu interface↔impl. Thêm cả cạnh mirror ngược chiều để đi được 2 chiều.
DB_LINK_EDGESRETURNS, READS, WRITES, PARAMETER_TYPENối method tới model dữ liệu.

BFS từ handler; trong lúc duyệt ghi nhận 3 ứng viên terminal, chọn theo thứ tự ưu tiên:

  • 1. DBModel gần nhất (gặp là break ngay) → complete = true.
  • 2. repoFallback: repository-method (springLayer='repository') gặp đầu tiên. Nếu nó có cạnh DB_LINK tới 1 DBModel thì append DBModel làm bước cuối & set complete=true.
  • 3. farthest: node xa nhất reachable (khi không có DBModel/repo).
  • Không reachable gì → flow chỉ gồm handler, complete=false.

Đường đi dựng lại bằng map parents (đường ngắn nhất terminal→start rồi đảo), mỗi bước kèm relationFromPrev. Chống cycle: visited Set; trần MAX_STEPS = 200.

⚠ Ngóc ngách reviewer cần biết:
• Vì DB_LINK gộp chung adjacency, một controller-method RETURNS/PARAMETER_TYPE thẳng tới DBModel sẽ cho flow 2 bước "complete" bỏ qua service/repository — "đường ngắn nhất" có thể là shortcut, không phải chuỗi gọi thực.
• Cạnh RESOLVE mirror 2 chiều có thể tạo hop lạ (impl → interface → impl khác).
• Mâu thuẫn doc/code: JSDoc nói complete khi "chạm repository-layer method HOẶC DBModel", nhưng code chỉ set complete=true khi chạm DBModel (repo mà không có DB_LINK → vẫn "Incomplete"). Panel hiển thị "⚠ Incomplete" cho các flow dừng ở repository.
• ambiguities (bước interface nhiều implementation) ĐƯỢC tính nhưng không được panel render — hiện là "dead data" với người dùng.

Bước 3 — Danh sách flow (listFlows, limit 80)

  • Endpoint flows: mỗi endpoint (vòng này KHÔNG break theo limit).
  • Root method flows: node Method có outgoing CALLS, không incoming CALLS, layer ∈ {controller, service, component}, flow ≥ 2 bước.
  • Cuối cùng sort (endpoint trước, rồi title) và slice(0, 80).
  • domain = tên class gốc bỏ hậu tố (Controller|Service|ServiceImpl|Repository|Manager|Component|Handler…) rồi humanize; fileCount = số filePath phân biệt; title = method path → terminalName.

Chọn flow — highlight (flowFocus.ts)

  • partition: node ∈ flow = foreground; edge in-flow = có trong edgeIds HOẶC cả 2 đầu ∈ flow (giữ highlight liên tục dù edge-id lệch).
  • reducer: node ngoài flow → hidden; trong flow → forceLabel, primary ×1.25 (zIndex 3), khác ×1.08; edge in-flow ×1.4 + màu theo loại; ngoài flow → hidden.
  • Panel DataFlowDetailPanel: các bước có index, màu theo loại node, springLayer badge, file rút gọn; bấm bước → center node.

Điểm cần soi

  • Trace thuần client, tính lại khi graphData đổi tham chiếu (kể cả realtime) → cân nhắc chi phí O(flows·(V+E)).
  • Endpoint > 80 → root flows bị loại & list cắt ở 80.
  • "complete" chỉ dựa DBModel; flow dừng ở repository luôn hiện Incomplete (doc lệch).
  • ambiguities không hiển thị — nếu muốn dùng phải bổ sung UI.
